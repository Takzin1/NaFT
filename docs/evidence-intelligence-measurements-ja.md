## 2. 変更影響解析：同じ614件・同じオラクルでの比較

`tests/lib/impact-matrix.cjs` は既存 `tests/impact-proof.test.js` と同じ行列をデータとして公開し、**既存解析器がコミット済みの `reports/impact-proof.json` と完全に同じ数値を再現する**ことをテスト内で確認しています。オラクルは変更前後を既存 `compileEvidence` で全再計算した意味論ビューで、どちらの解析器も呼びません。

| 指標 | 既存 `analyzeImpact` | 差分エンジン |
| --- | ---: | ---: |
| ケース数 | 614 | 614 |
| オラクルで意味が変化 | 429 | 429 |
| オラクルで意味が不変 | 185 | 185 |
| 正しく再検証（TP） | 429 | 429 |
| 正しく対象外（TN） | 78 | 185 |
| 過剰な再検証（FP） | 107 | **0** |
| **見逃し（FN）** | **0** | **0** |

差分エンジンの分類内訳は `SEMANTIC_CHANGE` 429、`PROVENANCE_ONLY` 181、`NO_OP` 4。加えて全614件で、差分適用後の状態が (a) 変更後の入力から作り直した状態と全ノードのハッシュで一致、(b) 既存 `compileEvidence` の結果と一致、(c) 変更前の状態を書き換えていない、ことを確認しました。影響を受けたClaimの総ノード 20,375 のうち再計算は 5,240（25.7%）で、これは演算回数であり時間ではありません（[生成レポート](../reports/evidence-intel-impact.json)）。

**読み方の注意**：過剰再検証が0件なのは、エンジンがオラクルと同じ意味論定義で「値が実際に変わったか」を見るためです。独立しているのは計算経路（オラクルは既存コンパイラ、エンジンはノード演算）です。`PROVENANCE_ONLY` の181件も記録のハッシュは変わるため、以前の人間判断は再利用できません。任意の制度方法論に対する健全性の証明ではありません。

## 3. 算定の再現性

- 独立オラクル：Python の `Fraction` で、加減乗除・最小・最大・3種の丸め（タイと負数を含む）442式の結果文字列が全て一致。合成Claim 60件の算術プレビュー、状態、使用係数の版、プログラム集計の正確な総和も、係数 `SYN-EF@2026.1`（2.5）と訂正版 `@2026.2`（2.4）の両方で一致。
- 浮動小数点との差：`0.1 × 0.7 × 1.1 × 3` は4通りの順序で正確な積が全て `0.231`、同じ順序の倍精度の畳み込みは複数の異なる値になる（テストで確認）。既存 `multiply` 仕様の値は互換のため変更していません。
- 環境間：headless Chromium 153 と Node 22 で、同じ7件のClaimの状態ダイジェスト、変更後ダイジェスト、レポートのハッシュ、APIレスポンスのハッシュが完全に一致（本セッションで1回実施。CI対象外）。

## 4. 性能（実測）

`node scripts/benchmark-evidence-intel.cjs --write` の結果（[生成レポート](../reports/evidence-intel-benchmark.json)）。環境：Node v22.23.4、Linux x64、Intel Xeon 2.10 GHz、論理4コア、単一プロセス。値はウォームアップ1回を除いた中央値（ミリ秒）。各シナリオは計測前に全再構築オラクル・既存実装との一致・監査ログの突合を通過しています。

### 4.1 全Claimの評価（状態が無いところから）

| Claim数 | 既存 `compileEvidence` 全件 | エンジン `eiBuild` | エンジン／既存 |
| ---: | ---: | ---: | ---: |
| 100 | 108.8 | 158.0 | 1.45 倍 |
| 1,000 | 1,071.1 | 1,396.8 | 1.30 倍 |
| 5,000 | 5,698.4 | 6,460.5 | 1.13 倍 |

**初回の全件評価はエンジンのほうが遅い**です（ノードごとの値ハッシュのため）。これは後の差分適用のための前払いです。

### 4.2 1件のClaimの証憑1件を置換

| Claim数 | 既存 `analyzeImpact`（状態なし） | 既存Claim単位キャッシュ | 対象Claimだけを既存で2回コンパイル（参考下限） | エンジン `eiApplyChange` |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 136.3 | 261.9 | 1.9 | 0.9 |
| 1,000 | 1,326.3 | 2,640.9 | 3.4 | 1.4 |
| 5,000 | 7,232.7（1回計測） | 上限1,000件のため対象外 | 1.8 | 3.5 |

- 既存 `analyzeImpact` に対する比は約153倍／938倍／2,078倍ですが、これは**既存APIが全Claimの旧パッケージを毎回コンパイルし直す**という設計差を測ったものです。対象Claimだけを手で再コンパイルする下限（1.8〜3.4 ms）と比べると、エンジンは同程度です。
- エンジンの再計算は7ノード、再利用14ノード、再ハッシュした入力10個で、Claim数によらず一定です。それでも時間が 0.9 → 3.5 ms と増えるのは、Claim表の浅い複製とメタデータ走査がClaim数に比例するためです。
- 既存のClaim単位キャッシュは、スナップショット検証で全文書を再ハッシュするため、**既存の全件解析より遅い**ことを確認しました。

## 6. 再現方法

```bash
bash tests/run.sh                                        # 全スイート
node tests/evidence-intel-impact.test.js --write         # reports/evidence-intel-impact.json を再生成
node scripts/benchmark-evidence-intel.cjs --write        # reports/evidence-intel-benchmark.json を再生成（数分）
```

`reports/evidence-intel-impact.json` は決定論的で、テストがコミット済みファイルとの一致を検査します。`reports/evidence-intel-benchmark.json` は時間を含むため環境ごとに変わり、一致検査の対象ではありません。
